# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`cctokmon` — a zero-dependency Bash terminal dashboard showing live Claude Code token usage, cost, and context window data. Full specification is in `claude-token-monitor-spec.md`.

**Stack:** Pure Bash 4.0+ · `jq` (required) · `tput` · `awk` · no other dependencies.

TokenMojo is the GUI on top of the same bridge files: a macOS menu bar app (`menubar/`, Swift) and a Windows tray app (`windows/`, C# / .NET 10 WPF).

## File structure

```
cctokmon.sh              # Main monitor — entry point
cctokmon-statusline.sh   # Companion statusline script (called by Claude Code on every interaction)
cctokmon-hook.sh         # Claude Code hook (called on session events) that appends each session's events to a log
cctokmon-worktree-init.sh  # SessionStart hook: initialises submodules in a new `.claude/worktrees/` worktree
cctokmon-tm.sh           # `tm`: starts or resumes Claude Code in the current tab and tags the tab title for TokenMojo
install.sh               # Installer: deps check, symlink, statusline and hook config
uninstall.sh             # Clean removal
config.example           # Config template copied to ~/.config/cctokmon/config on install
CLAUDE.md                # This file
claude-token-monitor-spec.md  # Original build spec (source of truth for design decisions)
menubar/
  TokenMojo.swift        # macOS menu bar app (AppKit + SwiftUI, single file)
  build.sh               # swiftc → ~/Applications/TokenMojo.app
windows/
  build.sh               # tests, then dotnet publish → %LOCALAPPDATA%\Programs\TokenMojo\TokenMojo.exe, plus a Start menu shortcut
  TokenMojo.Windows.slnx
  src/TokenMojo.Core/    # net10.0, no UI: bridge parsing, display rules, session loading, source discovery
  src/TokenMojo/         # net10.0-windows WPF tray app: icon, flyout, pop-out, launcher, Launch at Login
  tests/TokenMojo.Core.Tests/  # xUnit tests for Core (run on any OS)
```

## Running / testing

```bash
bash cctokmon.sh --check     # validate deps and data sources
bash cctokmon.sh --help
bash cctokmon.sh             # bridge mode (default)
bash cctokmon.sh --mode polling
bash install.sh              # or: cctokmon --setup
```

No build step — scripts run directly with bash.

Windows app (needs the .NET 10 SDK; Core tests run on Linux/macOS too, the app builds from any OS):

```bash
dotnet test windows/tests/TokenMojo.Core.Tests
bash windows/build.sh [target-dir]
```

## Key architecture

### Two operating modes

- **Bridge mode (default):** Claude Code calls `cctokmon-statusline.sh` on every interaction → writes JSON atomically to `~/.claude/cctokmon-state.json` → `cctokmon.sh` polls that file every `REFRESH_INTERVAL` seconds. Billing-accurate data.
- **Polling mode:** Reads `~/.claude/stats-cache.json` directly. No setup beyond install; shows daily/all-time totals only.

### Data source rules (critical)

- **Statusline JSON** — billing-accurate. Use `cost.total_cost_usd` directly in bridge mode; do not recalculate from tokens.
- **`stats-cache.json`** — accurate cumulative/daily totals.
- **JSONL `usage.input_tokens` / `usage.output_tokens`** — unreliable streaming placeholders (off by 100–174×). Do not use.

### Rendering

- `tput cup 0 0` for in-place refresh — no `tput clear` per frame (causes flicker). Clear only on first run and SIGWINCH.
- `tput ed` after each frame to erase stale content below (e.g. after resize).
- All float math via `awk`. No `bc`.
- Single `jq` call per data read with `mapfile -t arr` into indexed array.
- `SCRIPT_DIR` resolved via `readlink -f` at startup so `--setup` works through symlinks.
- `stat` mtime: macOS uses `stat -f %m`, Linux uses `stat -c %Y` — detected at runtime via `uname -s`.
- Always prefix `printf` with `LC_NUMERIC=C` when formatting floats (e.g. `LC_NUMERIC=C printf '$%.4f'`). Without it, locales using `,` as the decimal separator cause `printf: invalid number` and crash the script under `set -u`.
- Variables used across conditional branches must be declared before the `if` block. Declaring inside only one branch and referencing outside it triggers `set -u` and kills the process. (Historical example: `bar_w` was declared inside an `else` branch but used afterwards for the rate limit bar.)

### Installer (`install.sh`)

- Checks all deps (bash 4+, jq, tput, awk) before touching anything. The bash check is the first statement of the script, before `set -e` and any bash-4 syntax (`declare -A`, `${x,,}`, `mapfile`), written so that bash 3.2 can parse it: `[ "${BASH_VERSINFO[0]:-0}" -lt 4 ]`, no `[[ ]]`.
- Every script that needs bash 4 opens with that same guard and fails visibly: `cctokmon.sh` (before `declare -A`), `install.sh`, `uninstall.sh` and `cctokmon-tm.sh` print an error to stderr and exit 1; the two hook scripts print one line to stderr, never stdout, and exit 0 so a session is never broken. `cctokmon-statusline.sh` has no guard on purpose: it uses only bash 3.2 syntax (keep it that way: no `mapfile`, `declare -A`, `${x,,}`), so it keeps working under stock macOS bash.
- If deps are missing: detects package manager (brew / apt / dnf / yum / winget), shows what it will install, prompts once, then re-verifies.
- Symlinks `cctokmon.sh` to `~/.local/bin/cctokmon`. Under Git Bash on Windows (`uname -s` is `MINGW*`/`MSYS*`/`CYGWIN*`) it writes a small launcher script instead: `ln -s` there silently copies the file unless Developer Mode is on, and a copy cannot find `install.sh` for `--setup`. `uninstall.sh` removes either form.
- On Windows only jq needs installing (Git Bash ships tput and awk). winget's links dir is appended to `PATH` before the dependency check, since a shell opened before the install predates it; otherwise a re-run reinstalls jq and stops on winget's "no upgrade" error. The hook, statusline and worktree scripts append it too when jq is not on `PATH`, because a running Claude Code also predates it.
- Creates `~/.claude` if absent, then copies `cctokmon-statusline.sh` to `~/.claude/cctokmon-statusline.sh`.
- Optionally sets `statusLine` in `~/.claude/settings.json` via `jq`. The correct format is an object: `{"type": "command", "command": "\"/path/to/script\""}` — not a plain string (Claude Code's `/doctor` will flag a plain string as invalid). The command path is quoted inside the string, like the hook commands, because Claude Code runs it through a shell and HOME may contain spaces. Earlier installs wrote it bare: `install.sh` rewrites that form to the quoted one without asking, leaves the quoted form alone, and `uninstall.sh` removes the `statusLine` only when its command is exactly ours in either form, so a custom statusline script that merely has `cctokmon` in its name is left alone.
- Links `cctokmon-tm.sh` as `~/.local/bin/tm` the same way (a launcher marked `# tm launcher` under Git Bash). A `tm` it did not write is left alone, and `uninstall.sh` removes only ours.
- Copies `cctokmon-hook.sh` to `~/.claude/` and, prompting once, appends `{"hooks":[{"type":"command","command":"<dest>"}]}` to each of `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `Stop` and `SessionEnd` in `settings.json`. Idempotent, and other hooks are left alone. `uninstall.sh` removes only entries whose command is ours.
- Copies `cctokmon-worktree-init.sh` the same way and registers it, in the same prompt and idempotently, for `SessionStart` only, as `{"matcher":"startup","hooks":[{"type":"command","command":"<dest>","timeout":600}]}`. An install that already has the ten status hooks is still offered it, and one with only the original eight is offered the two subagent hooks. `uninstall.sh` removes both commands from `settings.json` before it removes either script.
- Every `settings.json` write goes through one `write_settings` helper per script (`install.sh`, `uninstall.sh`): it resolves a symlinked `settings.json` to the real file and writes there, builds the result in a temp file beside it (a same-filesystem `mv`), then applies the file's mode to the temp file with `chmod` after jq has written it (read with `stat -f %Lp` on macOS, `stat -c %a` elsewhere, chosen by `uname -s`), so a read-only `settings.json` works, and removes the temp file on any failure, leaving the original untouched. If the real file's directory is not writable it fails with a message naming that path. Do not add a write that bypasses it.
- A jq-captured value that is compared or used as a filename must have its trailing `\r` stripped: a native `jq.exe` under Git Bash ends every line with CRLF (`${v%$'\r'}`, or `mapfile -t` then `cr=$'\r'; arr=("${arr[@]%"$cr"}")`). Never write `"${arr[@]%$'\r'}"`: inside double quotes the `$'\r'` is not expanded, so it strips nothing.

### Worktree submodule hook (`cctokmon-worktree-init.sh`)

- A separate script, never part of `cctokmon-hook.sh`, which must stay a fast append: a submodule clone can take minutes, hence the 600 second timeout.
- It acts only when the payload's `cwd` contains `/.claude/worktrees/`, `.gitmodules` exists there, and `git submodule status` lists an uninitialised (`-`) entry; then it runs `git submodule update --init --recursive` with stdin from `/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and `GIT_SSH_COMMAND` set to the configured ssh command (`GIT_SSH_COMMAND`, else `core.sshCommand`, else `ssh`) plus `-o BatchMode=yes`, so nothing can wait for an answer. Windows-style `cwd` backslashes are turned into slashes first.
- Like the status hook it must never write to stdout (`SessionStart` stdout is added to Claude's context): `exec >&2` at the top. It always exits 0.

### Session status hook (`cctokmon-hook.sh`)

- The hook only appends. For each of the ten events it writes one line, `{"t":<epoch>,"e":"<event>"}` plus `"a"` (agent_id), `"n"` (notification_type) or `"s"` (source) when present, to `~/.claude/cctokmon-sessions/<session_id>.events` with a single `>>`, with the same `session_id` guard as the bridge. It takes no lock and reads no earlier state: a read-modify-write file lost events when hooks overlapped. Lines stay far below 4 KB so each append is one write. The `.events` extension keeps it out of the `*.json` scan, and the 7-day cleanup removes old ones.
- It must never write to stdout (`SessionStart` and `UserPromptSubmit` stdout is added to Claude's context) and must always exit 0. Nothing from prompts or tool input is logged.
- The main agent's state is worked out by the reader, `SessionEvents.Reduce(lines, now)`, applying lines in order and skipping any that are not complete events. Only events without `a` drive it: `SessionStart` (not `source` `compact`) → ready; `UserPromptSubmit` → working, starting a turn only from ready or no status (a subagent's result arrives as a second prompt mid-turn, so while working or needing input it keeps the turn start); `PreToolUse`, `PostToolUse` and `PostToolUseFailure` → working, which clears a needs-input prompt the main agent raised (a denied prompt is followed by the main agent's next tool call); `Notification` with `n` of `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog` or `agent_needs_input` → needs input, from any agent; `Stop` → ready; `SessionEnd` → ended. A tool event or a needs-input notification from ready or no status sets the turn start to its own time (a background wake, or a turn whose start fell outside the 64 KB window), so an old turn start never raises a finished alert. Ended changes only on `SessionStart`, not on a prompt, because a resume sends `SessionStart` first.
- Subagents never change the main state and never start or extend a turn. A `Notification` of a needs-input type records who raised the prompt, its `a` or else the main agent (other types, such as `idle_prompt`, never set or change the owner), and a prompt is cleared only by its owner: the main agent's by the main agent's own `PreToolUse`, `PostToolUse` or `PostToolUseFailure`; a subagent's by that same id's `PostToolUse` or `PostToolUseFailure`, its `SubagentStop`, or its expiry, which return to the state the prompt interrupted, or to working when the log began at the prompt. Events from any other agent leave it alone. A second prompt while one is open replaces it as the one shown and owned, and the first is not restored when it clears (a known limit). Reduce keeps a map of `a` id → last time seen: any event with `a` adds or refreshes the id, `SubagentStop` removes it whether or not its start was seen, and a non-compact `SessionStart` or a `SessionEnd` clears the map; an id not seen for 10 minutes (`SubagentLifetime`) counts as finished, evaluated against `now`, so a lost `SubagentStop` cannot pin the session. The displayed status is working when the main state is ready and at least one subagent is live, else the main state. `Since` is when the displayed status last changed, so it is stable across refreshes while nothing changes, even for events dated after `now`: it is never re-dated to `now`. Only the working → ready expiry is dated by the expiry moment `min(lastSeen + 10 min, now)`, the last `SubagentStop` dates a stop, and any other change found while settling uses the time being computed for. A `now` before the last line is treated as that line's time, so clock skew cannot revive an expired subagent. The turn start stays the main agent's. `SessionEventState.Subagents` is the live count, carried to `SessionSnapshot` and shown as `Working: N subagents`.
- Session ids are deduplicated once, in `SessionStore.LoadSessions` (newest `Updated`, ties broken by the events file's write time), so rows, the waiting count and alerts see one copy.
- `SessionStore` reads the last 64 KB of the file (dropping the partial first line). No file means no status; an unreadable file skips the session for that refresh.

### Config file

`~/.config/cctokmon/config` (or `$CCTOKMON_CONFIG`). Sourced after CLI args are parsed, so CLI args take precedence. Key settings: `REFRESH_INTERVAL`, `MODE`, `STATE_FILE`, `STATS_CACHE`, `THEME`.

### Pricing table

`declare -A PRICE_INPUT PRICE_OUTPUT` near top of `cctokmon.sh`. Used **only** in polling mode for cost estimation. In bridge mode `cost.total_cost_usd` from the statusline JSON is authoritative.

### `tm` (`cctokmon-tm.sh`)

- `tm [--wt NAME] [--prompt-file PATH] [--] [prompt...]` generates a session id, prints the OSC 0 title `TM <name> <id8>` (id8 is the first 8 characters of the id; name is `--wt` or the folder), then `exec`s `claude --session-id <id> -n <name> [-w NAME] [-- prompt]`. `tm --resume <id>` tags the tab the same way and runs `claude --resume <id>`.
- The session id comes from `/proc/sys/kernel/random/uuid`, else `uuidgen`, else (Git Bash, which has neither) a version 4 UUID built from 16 bytes of `/dev/urandom` with `od`.
- It exports `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`, because Claude Code otherwise rewrites the title; this also turns off Claude's own title updates and terminal status reports in that session.
- `--prompt-file` reads the prompt and deletes the file after argument validation and before any check that can exit (including the `claude` lookup); a failed delete is a warning, and a missing file is an error. Each run also deletes `~/.claude/cctokmon-launch/*.txt` older than a day. Bad arguments (unknown flag, missing value, a worktree name outside `[A-Za-z0-9._-]`) print usage to stderr and exit 2.
- Resuming does not depend on the folder: `claude --resume <id>` finds the session from the repository root, or any folder, after its worktree was removed (it continues without the worktree).

### Windows tray app (`windows/`)

- Shares everything outside the UI with the Mac app: the same bridge script, installer and file contract (`cctokmon-state.json`, `cctokmon-sessions/`, `CCTOKMON_STATE_FILE` / `CCTOKMON_SESSIONS_DIR`). Do not add a Windows-specific bridge; under native Windows, Claude Code runs the bash bridge through Git Bash.
- Display rules mirror `menubar/TokenMojo.swift` and must stay in step with it: `livePercent` (null once `resets_at` has passed), severity thresholds 50/80, the 12-hour session window, "active" within 10 minutes, at most 10 session rows, reset/percent/cost wording. The window and row count are only defaults on Windows: `sessionHours` (1 to 168, the bridge's 7-day cleanup) and `sessionRows` in settings change them, the alert baseline forgets sessions after the same window, and the rows scroll past about ten. They live in `TokenMojo.Core` (`Gauges`, `Dashboard`, `SessionStore`) so they are unit-tested; the WPF project only binds to `DashboardModel`.
- Sources: `ClaudeDirLocator` returns `%USERPROFILE%\.claude` plus `\\wsl.localhost\<distro>\home\*\.claude` (and `/root`) for distros listed by `wsl.exe --list --running --quiet` (UTF-16LE output). Only running distros are read, because touching a stopped distro's share boots it. Discovery reruns every minute; the bridge files are polled every 5 seconds off the UI thread. The Linux user of a source is the account that owns the home folder, never the folder name: per running distro `WslAccounts` runs one `wsl.exe -d <distro> --exec sh -c "id -un; getent passwd"` (no `-u`, so the first line is the default user; UTF-8 output, unlike the UTF-16LE `--list`) and `LinuxAccounts.Parse` maps home to account. Sources carry `Home` and `IsDefaultUser`; every tilde expansion, repo scan and `tm` path uses `Home`, never `/home/<user>`. `ClaudeDirLocator` keeps each distro's last successful answer (shared between the discovery timer and the launcher, so thread-safe) and reuses it when a query fails; only a distro that has never answered, or a home missing from its passwd, falls back to the folder name with a traced warning. A home shared by two accounts goes to the default user, else the first. Only `/home/<folder>` and `/root` are looked at; a `/home/root` folder is an ordinary home, never root's. `wsl.exe` calls go through `WslProcess` (blocking, 5 s timeout), never on the UI thread.
- Session status differs from the Mac app: the Windows app reads the hook's `.events` log (`SessionEvents`, `StatusAlerts`), so a row is needs input / ready / working / ended. Only a session with no events file falls back to the Mac app's 10-minute "active" rule. The list orders needs input, ready, working, no status, ended, then newest first, before the `sessionRows` cap.
- Alerts: a balloon tip on entering needs input, and on any change into ready after a turn of at least `longTurnSeconds` (default 30) from `%APPDATA%\TokenMojo\settings.json`. The first load is a baseline and alerts nothing. Finished is announced at most once per turn: a turn can show ready, working and ready again (a subagent expires, reappears, then stops), so the baseline's `SeenStatus.FinishedTurn` remembers the turn start it last announced, set by `Advance` whenever a session is ready after a long turn, and `Diff` skips a ready session whose turn start matches. A new main turn has a new start and can alert again. An existing settings file that is invalid is shown in the flyout and defaults are not used; when the file is absent and cannot be created, defaults are used. The tray ring's centre shows the waiting count (needs input plus ready) in place of the percentage.
- Click-to-focus and resume: `SessionWindows.Find` matches the `tm` tag's id8 as a whole token in the title of a Windows Terminal window (class `CASCADIA_HOSTING_WINDOW_CLASS`, whose title is the active tab's), `SessionActions.Decide` picks focus, confirm-resume or resume, and `ResumeCommand` builds the `wt.exe` argument list (a list, so paths with spaces survive; `-u` the session's Linux user; the folder is `workspace.project_dir`, else `current_dir`, then the repository root when the worktree is gone, then `~`; `tm` is called as `~/.local/bin/tm`, unquoted, since a login shell may not have it on PATH; the session id must be a UUID). Anything that touches the WSL share runs under `Task.Run`, never on the UI thread. All of it is in Core; `SessionControl`, `TerminalWindows` and `Native` only execute it. Sources carry their `Distro`; a Windows-source session (no distro) is resumed by `ResumeCommand.BuildNative` (see the native target below), in its folder, else the repository root (`WindowsFolder.RepositoryRoot`), else the user profile. A balloon is skipped when the foreground window's title matches the session, and clicking one focuses (or resumes) the first session it lists.
- Launcher (`LauncherWindow`, its own window because the flyout closes on deactivate): from the tray menu, the flyout menu and the "+" in the Sessions header; one window is reused. Core decides, WPF only executes. `LaunchHints.From` reads the first Linear issue or GitHub pull request URL (worktree `<team>-<n>` lowercase or `pr-<n>`; folder from `linearTeams`, or the scanned repo whose `origin` is `<owner>/<repo>`, else the first with any remote at `<owner>/<repo>`, such as a fork's `upstream`), `RepoScanner` lists repos one level under each `repoRoots` entry (a `.git` file is not a repo root; it never throws), `FolderList` orders default, recent folders, repos, and `LaunchCommand.Build` makes the `wt.exe` arguments through the same `TerminalCommand` base as `ResumeCommand`. A hint only fills fields the user has not chosen.
- The launch command is `wt.exe -w new wsl.exe -d <distro> -u <user> --cd <folder> -- bash -lc "~/.local/bin/tm [--wt NAME] [--prompt-file ~/.claude/cctokmon-launch/<guid>.txt]"`. The shell string must never hold a `;` (wt.exe splits its command there; arguments are escaped, but this one has nothing to escape) or a quote. The prompt goes through a file made by `LaunchPrompt`'s scripts (UTF-8, no BOM, LF) that `tm` deletes; `SessionLauncher` discards it if the terminal fails to start. The folder passes to `--cd` as given (`~`, `~/x`, `/x`), validated by `LinuxFolder.IsValid`; the worktree name by `tm`'s own rule. The user comes from `LaunchTargets.ChooseUser`: the distro's default user when it has a `~/.claude` and a `tm` that is ours, else the first source that has one; its `Note` explains a non-default choice. "Ours" is decided inside the distro, never over the share: `install.sh` makes `tm` a symlink to an absolute Linux path, which Windows cannot follow through `\\wsl.localhost` (`ReadAllText` throws, `LinkTarget` is empty). `WslTmInspector` runs `wsl.exe -d <distro> -u <user> --exec sh -c <TmInstall.InspectScript>`, which prints the first 4 KB of `$HOME/.local/bin/tm` following the link (exit 3 missing, 4 not a regular file, 5 found but unreadable), and `TmInstall.FromScript` looks for `install.sh`'s markers (a `# tm launcher` line, or a `# cctokmon-tm.sh` header) in that output. `WslProcess` returning null (not installed, or no answer within its one 5 s deadline, which covers the stdin write too and kills the process tree) is `TmState.Unchecked`; exit 5 is `TmState.Unreadable`; any other exit means wsl.exe or sh failed before the script ran (an unknown `-u` user, 127) and is `TmState.CouldNotRun`, whose message carries the exit code (`TmCheck` holds state and exit code; a bare `TmState` converts implicitly). None of these is ever called missing, and `WslProcess` catches every failure of start, read and kill by type and returns null. In `ChooseUser`, Missing, Foreign, Unreadable and CouldNotRun skip a user; Unchecked skips a non-default user but stops the search at the default one, so a session never silently starts as someone else; if nobody qualifies and any user was Unchecked, that is what is reported. Resume and launch both refuse anything but Ours, and the launcher checks again at Start. When the window finds no user at Start it asks again before giving up; if that changes the home, the scan in flight ends (`_generation` is bumped in `ApplyUser`) and a new one runs. Start's handler resets `_starting` and Cancel in a `finally` and shows, never throws, the errors that reach it; Start is enabled only while neither a launch nor a distro choice is in progress. Switching distro clears the user and home and disables Start until the new choice lands. While a launch is in flight Cancel is disabled and Closing is cancelled. The prompt file is not written over the share (it would be owned by the distro's default user, not the launch user): `WslPromptHandoff` runs `wsl.exe -d <distro> -u <user> --exec sh -c <LaunchPrompt.DepositScript>` with the prompt on stdin, so the file is created by the launch user (umask 077, noclobber) and the prompt is never on a command line; `Discard` removes it the same way when the terminal fails to start. Cancel/Esc in the launcher closes it (`IsCancel` alone does nothing for a window shown with `Show()`). Settings fields `sessionHours`, `sessionRows`, `distro`, `defaultFolder`, `repoRoots`, `windowsDefaultFolder`, `windowsRepoRoots`, `linearTeams` are validated on load like the rest of the file.
- Native Windows target (Claude Code on Windows itself, no WSL): `LaunchTargets.Targets` lists each running distro that has a Claude source (so Docker Desktop's distro is never offered; a distro named Windows, matched ignoring case like `IsWindows`, is left out so it cannot be taken for the native target), then `LaunchTargets.Windows` ("Windows") when `%USERPROFILE%\.claude` exists; `ChooseDistro` picks `settings.distro` among them, else the first, and the launcher's "Run in" picker shows them when there are two or more. A native session runs the same `tm` through Git Bash: `wt.exe -w new -p "Claude Code (TokenMojo)" -d <full Windows folder> <Git>\bin\bash.exe -c "exec ~/.local/bin/tm [...]"`, built by `TerminalCommand.NativeWindowArguments` (`LaunchCommand.BuildNative`, `ResumeCommand.BuildNative`). `bin\bash.exe`, not `usr\bin\bash.exe`, because it puts Git's tools on PATH itself; `-c`, not `-lc`, because Git Bash's login profile changes to the home folder. The `exec ` prefix is load-bearing: an argument without spaces reaches Git Bash unquoted, and its runtime expands a tilde in an unquoted argument before bash sees it, so `~/.local/bin/tm` would become a home path that splits at a space in the user name. `GitBash.Find` takes `CLAUDE_CODE_GIT_BASH_PATH` (either slash; mapping a `usr\bin\bash.exe` to the `bin\bash.exe` beside it when that exists), then `Git\bin\bash.exe` under `ProgramW6432`, `ProgramFiles`, `ProgramFiles(x86)` and `LOCALAPPDATA\Programs`, never System32's WSL `bash.exe`. Git Bash's `~` is `GitBash.Home`: `HOME` when it is a full Windows path (some machines set it to a network drive), else `%USERPROFILE%`; `SessionControl.GitBashHome` is used for everything `tm` reads (its own path and the prompt file), while a folder's `~` in the launcher stays the profile. `TmInstall.InspectLocal` reads the first 4 KB of `TmInstall.LocalPath(GitBashHome)` directly (install.sh writes a launcher there, not a symlink) for the same markers, and `LaunchTargets.NativeProblem` refuses anything but Git Bash plus a `tm` that is ours, checked when the launcher picks Windows and again at Start and at resume. Folders are `WindowsFolder` paths (a drive or UNC path, or `~`, `~\x`, `~/x` for the profile; no quote or control character), spelled out by regex rather than `Path.IsPathFullyQualified` so the Core tests mean the same on Linux; `settings.windowsDefaultFolder` and `windowsRepoRoots` (default `~`) are the native counterparts of `defaultFolder` and `repoRoots`. `linearTeams` values may be Linux folders or `WindowsFolder.IsWindowsOnly` ones (a drive, UNC or `~\x` path, which cannot be read as Linux); WSL takes only the Linux kind and Windows only the Windows-only kind, since `~` and `~/x` mean WSL in a setting both read. `RepoScanner.ScanWindows` reads the local disk, `FolderList.BuildWindows` takes sessions without a distro, Browse opens any local folder. The prompt file is written directly by `LocalPromptHandoff` into `<GitBashHome>\.claude\cctokmon-launch\<guid>.txt` (`FileMode.CreateNew`), the path `tm`'s `~` reaches. Both cleanup paths in `SessionLauncher` catch `IOException` and `UnauthorizedAccessException`, so a failed discard never replaces the failure being reported. `SessionLauncher.LaunchNative` keeps the same build-first, deposit, start, discard-on-failure order as the WSL launch.
- `TerminalProcess.Start` removes `TerminalCommand.ClaudeSessionVariables` (the variables Claude Code sets for its own child processes, such as `CLAUDE_CODE_CHILD_SESSION`) from the environment of every `wt.exe` it starts: a new Windows Terminal window gets the environment of whoever ran `wt.exe`, so a TokenMojo started from inside a Claude Code session would otherwise start sessions that take themselves for its children and save no transcript. User settings such as `CLAUDE_CODE_GIT_BASH_PATH` are kept; the list is explicit for that reason. It also starts `wt.exe` in the user profile: a WSL command has no `-d`, so the tab would open in TokenMojo's own working directory, which is wherever it was started from and fails the launch (0x8007010b) once that folder is deleted. The native command's `-d` still wins.
- Native sessions open in a hidden Windows Terminal profile, "Claude Code (TokenMojo)", only for its tab icon (wt.exe has no icon option). `TerminalProfileFragment.Ensure`, called once the tray icon is visible, draws the icon on the UI thread and writes it in a background task as a fragment (`TerminalProfile.FragmentJson`) with a drawn Claude-orange icon to `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\TokenMojo\`, rewriting only when it differs, so the user's `settings.json` is never written. Windows Terminal reads fragments only when it starts; until then the tab shows the default icon. A write failure is traced, not shown.
- The current state is the most recently written `cctokmon-state.json` across sources (rate limits are per account). Sessions from every source are merged into one list, newest first.
- Failures stay per source: a distro that stops or denies access mid-read is skipped, never allowed to blank the others or throw out of the timer tick. Bridge files are opened with `FileShare.Delete` so the bridge's `mv` can rename over a file TokenMojo is reading on Windows.
- Tray icon: one ring for the worst gauge, drawn by the same `RingGauge.Draw` as the dashboard rings and wrapped as a PNG `.ico`; taskbar light/dark comes from `SystemUsesLightTheme`, app light/dark from `AppsUseLightTheme`.
- `build.sh` publishes self-contained single-file without compression: compression halves the file size but roughly doubles memory, and the app runs all day.
- `build.sh` then writes `TokenMojo.lnk` to the user's Start menu Programs folder through `powershell.exe` (Git Bash or WSL; the exe path from `cygpath -w` or `wslpath -w`), passing the script with `-EncodedCommand` so no path needs shell quoting. Without either converter or `powershell.exe` it says so and skips the shortcut. `uninstall.sh` does not touch the Windows app, so it leaves the shortcut too.
- C# style is enforced by `windows/.editorconfig` with `EnforceCodeStyleInBuild` and warnings as errors: explicit types, never `var` (`IDE0008`); `new()` when the type is already written (`IDE0090`).
